# 评测方法

目标：每次改规则，都要证明新规则至少和旧规则一样懂 Stephen，不能越改越偏。依据是 Stephen 审核过的历史批次。

## 两层评测

| 层 | 测什么 | 怎么跑 | 花费 |
|---|---|---|---|
| 程序层 | 一票否决和排序会不会误伤 Stephen 选过的文章 | `eval_replay.py machine`，几秒钟 | 无 |
| 判断层 | Agent 按当前 SKILL 读全文打分，结论和 Stephen 一不一致 | `export` 导出盲评集，子 Agent 判断，`score` 对照 | 读稿用量 |

程序层每次改规则都跑。判断层在改终审标准、改六维打分、改正反例之后跑。

## 基准集

```bash
.venv/bin/python3 scripts/eval_replay.py build
```

- 从 `.local/editorial_feedback.jsonl` 取每篇文章最后一次的结论，待定不算。
- 冻结成 `.local/eval/benchmark-v001.jsonl` 这样的版本文件，旁边有清单（条数、来源文件指纹）。有新反馈时生成新版本，旧版本保留，同一版本的结果才能互相比较。
- **按批次切分**：约 70% 的批次做开发集，用来调规则；约 30% 做留出集，平时不看，只在大改之后检查有没有“只是记住了开发集”。同一批次的文章不会同时出现在两边。
- 写正反例、改判断标准时，只能引用开发集里的文章，不能引用留出集的标题和原话，否则留出集就测不出过拟合。`eval_replay.py leak-check` 会检查。
- 每条标上**标签强弱**：有单条原因（标签或针对这一篇的备注）是强标签；整批评语、空白、没点默认“不要”的是弱标签。两类分开统计。
- **写成文章是最强的标签**：`.local/eval/adoptions.json` 记录哪些候选被 Stephen 写成了文章（对照 `.local/articles/` 里同步下来的已发布文章）。这些候选一律按入选计，标签强度记为 `adopted`，覆盖审核页上的结论；没打标的批次里被写成文章的候选也会补进基准集。每次同步到新文章后，补充对照关系再重新 `build`。
- 正文不足 800 字的记录不参与判断层（存下来的正文不完整，没法重新判断）。

## 程序层看什么

```bash
.venv/bin/python3 scripts/eval_replay.py machine
```

- **选中保留率**：Stephen 选过的文章，按新规则有多少没被一票否决。目标 100%。低于上次就报退步并返回失败。
- **排序区分度（AUC）**：随便抽一篇选中的和一篇淘汰的，选中那篇在阅读顺序里排在前面的概率。0.5 等于瞎排。阅读顺序现在只看来源优先级和新鲜度，Agent 还会自己通读全部标题，所以这个数只作参考。
- 每次结果记入 `.local/eval/history.jsonl`，带提交号，可以用 `history` 查看趋势。


## 判断层怎么跑

1. 导出盲评材料（不含 Stephen 的结论）：

```bash
.venv/bin/python3 scripts/eval_replay.py export --split dev --output .local/eval/blind-dev.json
```

2. 按来源拆给子 Agent。每个子 Agent 只拿到当前 SKILL.md、编辑判断标准、正反例和分到的材料，逐条读全文、按六维打分，输出：

```json
[{"id": "...", "verdict": "recommend", "scores": {"topic_appeal": 2, "...": 1}, "reason": "一句话理由"}]
```

`verdict` 只能是 `recommend` 或 `reject`，按 SKILL 的打分规则得出。子 Agent 不能看到历史反馈、审核结论或本评测的指标。

3. 对照 Stephen 的结论：

```bash
.venv/bin/python3 scripts/eval_replay.py score .local/eval/verdicts-dev.json --split dev --judge claude-opus-5
```

## 指标怎么读

历史上 Stephen 只选了约 12%。这意味着“全部判不要”的准确率也有 88%，所以**不用准确率当目标**，看这三个：

- **选中召回**：Stephen 选过的，Agent 也推荐了多少。这是“别把好题判错”，对应“之前的判断标准都要吸收”。目标 ≥ 95%。
- **推荐命中率**：Agent 推荐的，有多少是 Stephen 选过的。它决定审核页的质量。目标先定 ≥ 40%（现在的真实采纳率约 12%，一批 10 条里至少 4 条能用），逐步往上提。
- **平衡准确率**：选中召回和“淘汰识别率”的平均，不受比例影响。

每次输出都会列出两份清单，比分数更重要：

- **漏掉的好题**：Stephen 选了、Agent 没推荐。逐条看 Agent 的理由，找出是哪条规则误伤，改规则或补正反例。
- **多推荐的**：Agent 推荐、Stephen 没选。看 Stephen 的原因标签，判断是标准写得不清，还是弱标签本身不可靠。

## 回归门槛

- 程序层：选中保留率不能下降。
- 判断层：同一基准版本、同一切分，选中召回或平衡准确率下降超过 0.02 就报退步，要先解释或修正再提交。
- 大改（改打分规则、改正反例超过三处）后，额外跑一次留出集。开发集涨、留出集跌，说明规则只是记住了开发集。
- 判断一致性：同一批材料隔几天再判一次，或让两个子 Agent 独立判，一致率低于 85% 说明标准写得不够清楚。

## 当前基线

开发集固定抽样 60 篇（Stephen 选中 24、淘汰 36），留出集 33 篇（选中 6、淘汰 27）。数字已叠加一票否决；“估计真实命中率”按 Stephen 历史约 12% 的入选比例换算，表示一批推荐里大约有多少他会选。从 v4 起用基准 v002，加入了“写成文章”的标签；“采纳集”是 7 篇被写成文章、此前没参与过盲评的候选，混入 5 篇淘汰稿一起盲评。

| 版本 | 开发集召回 | 留出集召回 | 采纳集 | 估计真实命中率（开发 / 留出） |
|---|---|---|---|---|
| 旧标准（五维逐项过关） | 17% | 未测 | 未测 | 约 17% / 未测 |
| v1（六维打分，总分至少 8 分） | 42% | 未测 | 未测 | 29% / 未测 |
| v2（关键词退出，前五维至少 6 分，按入选构成重写正反例） | 79% | 83% | 未测 | 26% / 20% |
| v3（AI 写作检查、收紧工程架构类、放宽工具和主流发布） | 96% | 83% | 5/7 | 44% / 31% |
| v4（加入已发布文章的类型：概念科普、企业落地、当天发布） | 92% | 83% | 7/7 | 31% / 20% |
| **v5（收紧产品战略分析、空泛企业评论、二手总结稿）** | **92%** | **83%** | **7/7** | **43% / 31%** |

v5 是当前版本：命中率回到 v3 的水平，同时把“本体”科普和 RSI 这类被写成文章的选题找了回来。开发集两次召回的差别来自一篇边界材料（视频逐字稿，Stephen 评价“还可以，但是逐字稿不易读”），在两次盲评之间来回变，属于评审波动。

v5 仍然多推荐的，主要是：截图或视频依赖（历史材料没有图片数，新抓取已经记录）、Agent 没认出来的 AI 写作、个人项目复盘、泛泛的个人感受。另有几条是标签本身的问题：整批拒绝没有单条理由、与另一个窗口重复被驳回。

`score` 的 `--judge` 用来区分评测对象，只有同一基准、同一切分、同一 `--judge` 的结果才会互相比较是否退步。`--no-gate` 只看 Agent 本身，不叠加一票否决。

## 局限

- 基准集只覆盖 Stephen 审过的文章，测不出系统漏掉的全网好文。
- 早期反馈很多是整批淘汰、没有单条原因，是弱标签。新审核页的原因标签会逐步改善这一点。
- Stephen 的口味会变。旧批次和新口味冲突时，以新反馈为准，并在新版本基准里体现。
