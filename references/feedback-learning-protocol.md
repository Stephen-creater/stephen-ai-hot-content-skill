# 反馈学习规则

这份规则说明怎样从 Stephen 的审核里学东西：留住他真正的判断，同时不让一次反馈变成永久补丁。

## 审核页收什么

- **按钮**：要这个 / 不要 / 待定。导出时没点的默认记为“不要”，并标上 `implicit: true`。
- **原因标签**：一键选，可多选。不要：题目没意思、对读者没用、太浅太泛、AI 味重、太依赖作者个人经历、太技术、太垂直小众、过时或已写过、改写成本高、广告或新闻通稿。要：读者痛点强、干货足、改一改就能发、长期有用、访谈或文字稿质量高。
- **整批问题**：页面顶部可以给整批点标签。
- **备注**：标签说不清时才写。

没点的记为“不要”，是为了让评测有完整的标签。这类记录只算结果，不当作原因来学习。

## 先存事实，再谈规则

每次导入完整保存批次、认领、候选、按钮、原因标签、备注和时间。原始记录只进 `.local/editorial_feedback.jsonl`，不提交。

然后把能学到的东西归成一类：

| 类型 | 意思 | 可以写进哪里 |
|---|---|---|
| `invariant` | 多个批次反复成立的原则 | 编辑判断标准 |
| `conditional_preference` | 满足某些条件才成立的偏好 | 正反例或配置 |
| `operational_rule` | 条数、顺序、认领、清理这类执行规矩 | SKILL.md 或代码 |
| `topic_state` | 写过、暂缓、不认可的具体产品或来源 | 已写主题清单、屏蔽名单 |
| `case_only` | 只适用于这一篇 | 只存档，不升级 |
| `unexplained_decision` | 点了按钮但没给原因 | 只记结果 |
| `hypothesis` | 也许能推广，但证据不够 | 先观察，等更多反馈 |

## 什么时候能变成规则

满足任意一条才能成为稳定原则：

- Stephen 明确说“以后”“一定”“硬性要求”“写进 Skill”；
- 不同主题、来源和内容形态反复出现同一判断；
- 新原则能同时解释选中和淘汰的例子，并能预测没见过的文章。

单个标题、产品名、作者名、技术词和一次情绪化评价，不能单独变成普遍规则。

### 审稿提示词的门槛

- 新增一类审稿提示词可以，但它默认只提醒、不扣分。
- 想让某类提示词降低阅读顺序，必须先跑 `.venv/bin/python3 scripts/eval_replay.py hints`：它在历史回放里从未命中过入选文章，且命中过至少 2 条、来自至少 2 个批次的淘汰文章。Stephen 明确说过“以后不要”的例外。
- 改完跑 `eval_replay.py machine`，Stephen 选中过的文章一条都不能被拦下。

## 写新规则前先找反例

写任何新原则前回答四个问题：

1. 历史上有没有同样表面特征却被选中的文章？
2. 真正让结果不同的条件是什么？
3. 规则能不能写成因果判断，而不是一串词或一个类别？
4. 换掉产品名、作者名和标题措辞，规则还成立吗？

答不上来，就只能记为 `case_only` 或 `hypothesis`。

## 冲突怎么处理

- 按钮决定这一条的结果，原因标签和备注决定能学什么。
- 按钮和备注明显矛盾时，保留原始记录，学到的东西记为 `hypothesis`，不强行解释。
- “已写过”优先当作 `topic_state`，不把入选按钮当成可以再推荐。
- 没有原因的淘汰只进去重历史，不产生新的负面原则。
- 待定不算入选也不算淘汰。

## 改规则前先写一段学习记录

```text
观察：Stephen 对哪些材料做了什么判断
类型：invariant / conditional_preference / ...
原则：能跨案例复用的因果判断
反例：哪些相似材料不该被一起误杀
放在哪里：文档 / 精确配置 / 代码 / 测试 / 只存档
评测：改前改后 eval_replay 的结果
```

## 测试要求

每条进入代码的编辑规则至少要有：

- 一个应该拦下的例子；
- 一个表面相似但应该保留的反例；
- 一个换掉具体名词后的变体；
- 对失败原因或证据字段的断言。

测试不能只证明某个词还能触发，要证明决定结果的是背后的条件。

## 标题预筛怎么评估

检查标题预筛是否有效时，好题保留率和坏题放行率要分开统计，两个都要报。不能用“全部拒绝准确率也很高”来证明有效。
