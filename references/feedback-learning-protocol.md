# 反馈学习协议

本协议规定如何从审核反馈中学习，目标是保留 Stephen 的认知，同时避免一次反馈变成永久补丁。

## 先保存事实，再抽象规则

每次导入必须完整保留批次、归属、候选、按钮状态、备注原文和时间。私有原文只进入 `.local/editorial_feedback.jsonl`，不得提交。

然后将学习结论归入一种类型：

| 类型 | 含义 | 可进入哪里 |
|---|---|---|
| `invariant` | 多批次稳定成立的核心原则 | 编辑判断模型 |
| `conditional_preference` | 满足特定条件才成立 | 校准案例或配置 |
| `operational_rule` | 数量、顺序、归属、清理等执行规范 | SKILL 工作流或代码 |
| `topic_state` | 已写、暂缓、具体产品或来源状态 | 精确配置与历史库 |
| `case_only` | 只能解释当前材料 | 私有反馈，不升级 |
| `unexplained_decision` | 有按钮但无可学习理由 | 只记录结果 |
| `hypothesis` | 可能可泛化，但证据不足 | 校准区，等待新反馈 |

## 升级门槛

反馈只有满足以下任一条件，才可成为稳定原则：

- 用户明确说“以后”“高优先级”“硬约束”“一定写进 Skill”。
- 多个不同主题、来源和内容形态反复出现同一判断。
- 新原则能够同时解释正例和反例，并能预测未见案例。

具体标题、产品名、作者名、单个技术词和单次情绪化评价不得独自成为普遍规则。

## 反例检查

写入任何新原则前必须回答：

1. 历史中是否存在命中同一表面特征却被入选的案例？
2. 真正导致结果不同的条件是什么？
3. 规则能否写成因果判断，而不是词汇或类别？
4. 换掉产品名、作者名和标题措辞后，规则是否仍有效？

如果不能回答，结论只能标为 `case_only` 或 `hypothesis`。

## 冲突处理

- 按钮状态决定该候选当前结果。
- 备注决定系统能够学习什么。
- 按钮与备注明显冲突时，保留原始记录，将学习结论标为 `hypothesis`；不得强行解释。
- “已写过”优先解释为 `topic_state`，不把入选按钮当成可再次推荐。
- 空备注淘汰只进入去重历史，不产生新的负面原则。
- 待定不算入选或淘汰，不改变正负偏好权重。

## 修改规则前的输出

每轮优化先形成简短学习记录：

```text
观察：用户对哪些材料作了什么判断
类型：invariant / conditional_preference / ...
稳定原则：能跨案例复用的因果判断
边界反例：什么相似材料不应被一起误杀
落实位置：文档 / 精确配置 / 代码 / 测试 / 仅私有历史
```

## 测试要求

每个进入代码的编辑规则至少需要：

- 一个应拦截案例。
- 一个表面相似但应保留的反例。
- 一个换掉具体名词后的变体。
- 对应的失败原因或证据字段断言。

测试不应只证明某个词还能触发；要证明决定结果的是背后的条件。
